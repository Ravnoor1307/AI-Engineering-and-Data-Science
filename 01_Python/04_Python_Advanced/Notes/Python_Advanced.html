Welcome to Object-Oriented Programming

So far your Python programs have lived inside modules and functions. You have used len(), append() and upper(), but you have never built a type of your own. This session changes that. Object-Oriented Programming (OOP) is the idea that data and the operations on that data travel together as one unit — an object. Python is an object-oriented language: every value you touch, from a simple integer to a complicated list, is an object that belongs to some class. In this session you will learn to design your own classes, stamp out your own objects, and control how Python's operators behave on them.

What you will learn
  1. Function vs Method — which one to use when
  2. Creating objects — using a class
  3. Defining a class + its constructor
  4. self and instance attributes
  5. Magic methods (__init__, __str__, __add__) — operator overloading
The mental model

Think of a class as a blueprint or cookie-cutter and an object as the cookie made from it. The blueprint declares which attributes every cookie should have (flavor, size) and which powers (methods) they all get. When you call the class, a fresh cookie is baked with its own private copy of each attribute. Two objects from the same class look alike on the surface but live in different memory — each carries its own state.

Key definitions
  • Class: a template/blueprint that bundles data (attributes) and behavior (methods).
  • Object: a concrete, live instance built from a class.
  • Constructor: the __init__ method that automatically runs when an object is born.
  • Method: a function defined inside a class and called with object.method().
  • Attribute: a piece of data owned by an object, written object.attribute.
  • Magic method: a dunder (__...__) method Python calls behind the scenes for operators and built-ins.

In the cells ahead you will first feel the difference between functions and methods, then build a class, study self, and finish with a tiny Fraction class where +, -, *, / do real fraction arithmetic. By the end you will be able to create reusable, self-contained types just like Python's built-in list and str. Before you start, remember the shorthand: a function takes the object as an argument (len(L)), while a method is called with a dot inside the type (L.append()).

What is OOP

Object-Oriented Programming models entities as objects with state (attributes) and behavior (methods).

Why

Encapsulation, reusability, abstraction, maintainability.

Core ideas

Class (blueprint), Object (instance), Encapsulation, Inheritance (later), Polymorphism (later).

  1. Function vs Method

1.1 Methods are attached, functions are standalone

Before you write your own classes you need to see the exact difference between a function and a method, because you will be creating methods all session.

  • A function lives outside any type. You call it by passing the data in: len(L), max(L), sorted(L).
  • A method lives inside a type and is reached with a dot: L.append(4), L.sort(), s.upper().

The dot is the key clue: object.method(). When you write L.upper(), Python looks inside the list class, finds no upper, and raises AttributeError: 'list' object has no attribute 'upper'. Similarly s.append('x') fails because strings have no append.

Call style Example Meaning
Function len(L) pass the object in as an argument
Method L.append(4) the object calls its own behavior

This is the foundation of abstraction: data and the operations that make sense for that data live in the same place. A list knows how to append, sort and pop; a string knows how to upper, split and strip. Each type carries its own little toolbox.

1.2 Deep dive — everything is an object

An object is a bundle of state (data) and behavior (methods). Every object in Python — an integer, a string, a list, a function — is an instance of some class, and it arrives with the methods of its own type. type(L) returns <class 'list'>, which tells you which toolbox the object carries.

  • Methods are attached to an object: object.method(arguments).
  • Without attached methods you would have to write a separate function for every data type.
  • OOP lets you define your own custom types so the "toolbox" can be exactly what your problem needs.

L is a list object: it can append, sort, and reverse, but it has no idea what upper means. s is a string object: it can upper and split, but it cannot append. The error is the class telling you clearly: "this operation does not exist in my toolbox." You will see both AttributeErrors when you run the two cells below — that is intentional and instructive.

  1. Magic Methods & Operator Overloading

9.1 Making + and print understand your class

Python reserves a set of "dunder" (double-underscore) methods for special operations. When you use an operator or a built-in, Python quietly translates it into a magic-method call.

Magic method Operator / built-in
__str__ print() and string conversion
__add__ +
__sub__ -
__mul__ *
__truediv__ /

By defining these on your own class you overload the operators — you decide what + means for your objects. The Fraction class coming up defines __str__ so print(fr1) shows 3/4, and __add__ so fr1 + fr2 performs real fraction addition. Same operators, your own meaning — this is operator overloading, and it is exactly how Python lets a class feel like a built-in type to everyone using it.

python
fr1 + fr2      # → fr1.__add__(fr2)
print(fr1)     # → uses __str__ / __repr__
len(L)         # → L.__len__()

Magic methods & operator overloading

  • __init__(self, x, y) — constructor with arguments
  • __str__ — gives a readable output for print(fr1)
  • __add__ / __sub__ / __mul__ / __truediv__ — operator overloading
  • fr1 + fr2 internally calls fr1.__add__(fr2)
python
class Fraction:
    def __init__(self, x, y):     # parameterized constructor
        self.num = x
        self.den = y

    def __str__(self):            # what is shown on print
        return '{}/{}'.format(self.num, self.den)

    def __add__(self, other):     # define + in our own way
        new_num = self.num * other.den + other.num * self.den
        new_den = self.den * other.den
        return Fraction(new_num, new_den)

  1. Encapsulation

8.1 Private data behind public gates

Encapsulation hides an object's internal state behind methods so outside code cannot pounce on it directly:

  • __name (double underscore) marks an attribute private via name mangling.
  • Direct access from outside fails; code must use the methods.
  • Getters read, setters write, and setters can validate — e.g. accept only integers.
  • Benefits: change internal logic later without breaking callers, and keep state consistent (invariants).

Privacy is a strong convention, not a hard wall — the mangled name _Atm__balance still technically works, but touching it is discouraged. Enforce the contract with a public method and private storage; the reader of any other class then knows instantly which names are "for internal use" without reading documentation.

python
class Atm:
    def __init__(self):
        self.pin = ''          # public attribute
        self.__balance = 0     # private — __ prefix

    def get_balance(self):
        return self.__balance   # gatekeeper (read)

    def set_balance(self, value):
        if type(value) == int:
            self.__balance = value   # gatekeeper (write, with validation)

  1. Class Relationships (Has-A / Is-A)

1.1 Aggregation — the Has-A relationship

Objects rarely live alone; more often one object contains another:

  • Aggregation (Has-A) — a class holds an object of another class as one of its attributes.
  • A Customer has an Address; an Employee has a Department; a Car has an Engine.
  • The contained object usually exists on its own (an address makes sense without a customer) — this loose coupling makes aggregation flexible.
  • You reach inside with the dot chain: cust.address.city.
  • Class diagrams draw it with a hollow diamond on the container side.

The customer example coming up also shows methods delegating to the contained object: edit_profile updates the address by calling self.address.edit_address(...) — one object asking another to take care of itself.

Does one thing contain another? Aggregation (Has-A) nested attribute Customer has Address

  1. Inheritance — the Is-A Relationship

2.1 One class wearing another's clothes

Inheritance creates a parent-child relationship between classes:

  • Syntax: class Child(Parent):.
  • The child receives the parent's non-private attributes and methods — it can use them as its own.
  • Is-A: a Student IS-A User.
  • Benefits of inheritance:
    • Code reuse — you never rewrite the parent's logic.
    • Extension — the child adds its own methods and attributes on top.
    • Overridability — the child replaces parent methods, the seed of polymorphism.
    • Hierarchy — modeling the world as families (Vehicle → Car → ElectricCar).

The most common confusion: inherited members become accessible, not mandatory — the child decides what to use, override, or extend. Think of the child as the parent plus a few extra powers: it can use the inherited rooms (attributes and methods), owns new rooms of its own, and may remodel a kitchen (override a method) without tearing down the architecture.

  1. The Super Keyword

4.1 Reaching back to the parent

super() is Python's reference from the child up to the parent:

  • super().__init__(...) invokes the parent's constructor explicitly.
  • super().method() calls a parent method you overrode, e.g. super().buy().
  • Use it when the child wants BOTH the parent's setup AND its own extras.
  • super can reach the parent's public and protected members, but not its private mangled names.
  • It is meaningful only inside a child's methods — there is no sensible super() outside the class body.

The pattern to internalize: override, then extend — in the child's version, do your own work, then call super().whatever() to keep the parent's behavior flowing. A useful test: if you catch yourself copy-pasting the parent's __init__ body into the child, stop — that is exactly the duplication super() exists to remove. Write the child's extras, and one line brings in everything the parent already does.

  1. File Input/Output in Python

1.1 Text Data vs Binary Data

Every file on your hard disk is ultimately a sequence of bytes. What differs between file types is how those bytes are interpreted.

  • Text data — for example the string '12345' — is stored as a sequence of Unicode characters, with each character encoded into one or more bytes (usually UTF-8).
  • Binary data — for example the number 12345 — is stored as the raw bytes of its binary equivalent, with no character interpretation at all.

That distinction produces the two file families you deal with:

Kind Examples Content
Text files .txt, .md, .csv, .json, source code human-readable characters
Binary files images, music, video, .exe, PDFs machine-oriented bytes

When Python opens a file in text mode it decodes the bytes into str objects; when it opens a file in binary mode it hands you raw bytes. Confusing the two is one of the most common beginner errors — and it is exactly what the mode argument of open() controls. Throughout this session, keep asking yourself: is the file I am touching text or bytes?

1.2 The Three Steps of File I/O

Almost every programming language follows the same ritual when working with files:

  1. Open a file — call open(path, mode) and get back a file object (your handle on the file).
  2. Read or write data — push text or bytes through that handle.
  3. Close the file — call f.close() when you are done.

Think of a file handle like a telephone line. Without open() there is nothing to talk to; without close() the line stays occupied and the operating system resource (a file descriptor) is left dangling. Step 3 is easy to forget but it matters: an unclosed file can stay half-written on disk, stay locked against other programs, or leak memory, especially in long-running scripts. The memory buffer of an unclosed file may never reach the disk.

The mode string you pass to open() decides what step 2 is allowed to do. The next several cells dig into the write side first — starting with the most common (and most dangerous) writing mode, 'w'.

2.2 The Dangers of ‘w’ — It Wipes Everything

Open a file with 'w' and the old contents are gone before the first write. In the code below, sample.txt previously held 'Hello world'; opening it with 'w' and calling f.write('salman khan') replaced the entire file — and there is no undo button.

This truncate-then-write behaviour is the classic file-handling bug: you open a file with 'w' intending to add a line, and silently destroy the previous data. Here is the mode decision table to memorise:

Mode Effect on existing content
'w' Truncates (erases) everything, then writes
'a' Keeps everything, appends new data at the end
'r+' Keeps everything, allows reading and writing
'x' Exclusive create; fails if the file already exists

Rule of thumb: never open a file with 'w' unless you are certain the old data is disposable. When you only need to add to a file, reach for 'a' first.

Choosing The Right Mode

Mode Behaviour
'r' read only (the default)
'w' write; truncates existing content
'a' append; keeps existing content
'x' exclusive create; fails if the file exists

Pick 'a' when preserving old data matters and keep 'w' for fresh rewrites. This single habit prevents most accidental data-loss disasters.

2.3 Append Mode — ‘a’

Append mode answers the question: how do we add to a file without destroying what is already there? Opening with 'a' keeps all existing content and places the file pointer at the very end, so every write() adds new characters after the last line.

Notice the difference from 'w':

  • 'w' empties the file the moment it is opened.
  • 'a' never removes content; it only extends the file.

Truncation is not 'delete then write': the moment open('sample.txt', 'w') executes, the file's length is cut to zero, and the write that follows lands in an empty file.   1. Context Managers — the with Statement

5.1 Automatic Resource Cleanup

Calling f.close() manually works, but it is easy to forget — and if an exception jumps out of the middle of a block, the close() line may never run. Python's answer is the context manager: the with statement guarantees cleanup when the block ends, whether it ends normally or with an error.

When the indented block finishes, Python automatically calls close() on the file object — no explicit close() required, no resource leak, and cleanup happens even if an exception is raised inside. That is exactly why the next cell fails: after the with block, the handle f is closed, and f.write('hello') raises ValueError about operating on a closed file.

Under the hood with relies on two magic methods, __enter__() (runs at the start and returns the object bound to as) and __exit__() (runs at the end and performs cleanup). Files, sockets, database connections and locks all implement this protocol, which is why with is the modern, idiomatic way to handle resources in Python. The third cell re-opens sample.txt for reading inside a with block and confirms readline() still works reliably.

6.1 Reading In Chunks

7.1 Text Mode vs Binary Mode

Everything so far assumed textual data, but many files — images, music, videos, compressed archives, PDFs — are binary. Every file is a bag of bytes; text mode simply means "decode those bytes as text". 11.1 How Pickling Works

JSON shines when the data must travel between languages or live in readable text. But for Python-to-Python storage there is a faster, more faithful route: pickle. Pickling is the process whereby a Python object hierarchy is converted into a byte stream; unpickling is the inverse operation, whereby a byte stream (from a binary file or a bytes-like object) is converted back into an object hierarchy.

Because pickle stores the object's type information together with its payload, almost anything survives the round trip: custom classes, functions, generators, nested structures — none of which JSON can touch without a hand-written encoder. The price is a binary format: pickled data is not human-readable, and it is Python-specific, so a pickled file is useless to a program written in another language.

The code defines a friendly Person class (name + age) with a display_info() method and creates one instance. A key fact: the class definition must be importable at unpickling time, because the byte stream references the class by name rather than copying its code.

  1. Syntax Errors — Failing Before You Run

1.1 What Is A Syntax Error?

A syntax error means the program text does not follow the grammar of the Python language. It is detected by the interpreter while the code is being parsed — before a single statement executes.

Key facts to remember:

  • The error is raised by the compiler/interpreter during compilation, not by your logic.
  • The program never runs; the parser fails immediately.
  • It is fully fixable: correct the offending line and the obstacle disappears.
  • The message usually points at the exact line and leaves a caret (^) under the spot where the parser got confused.

Think of syntax as the road signs of a language. A program with a syntax error is like a sentence with a broken word — a human can sometimes guess the meaning, but Python will not. Grammar mistakes block everything else, so they always have the highest debugging priority.

  1. Handling Exceptions — try / except

3.1 Why Handling Matters

Exceptions are raised by the Python runtime whenever something unforeseen happens during execution: memory pressure, division by zero (a logical error), a missing resource, a failed network call, a database error. Without handling, such an exception crashes the whole program and dumps an ugly error in the user's face.

Handling flips that: you place the risky operation inside a try block, and the fallback behaviour inside an except block. If nothing goes wrong, except is skipped; if an exception appears, the try block is abandoned at that point and the matching except handler takes over.

The user sees a friendly message and the program keeps running instead of dying. That is the entire motivation for this session: handle failures where they can happen, and let the user continue.

sql
try:
    with open('sample1.txt', 'r') as f:
        print(f.read())
except:
    print('sorry file not found')

3.2 The try / except Pattern

try/except is Python's safety net. The mechanics are simple:

  • The try block holds the code that may raise an exception.
  • The except block holds the fallback that runs if an exception occurs.
  • If the try block completes without errors, the except block is ignored entirely.
  • If an exception occurs partway through try, control jumps immediately to except and the rest of the try body never runs.

A bare except: catches literally anything — convenient for demos, but a clumsy production habit because it swallows the error without telling you which exception it was. The common files are handled with specific except clauses (next topic). A warning: even except Exception as e: is a broad net; the idiomatic path is to catch the specific exceptions your code can actually react to.

3.3 What Happens Inside try

A note on how the net behaves:

  • Once an exception is raised, the remainder of the try block is skipped — statements after the failing line never execute.
  • The matching handler is the first except clause whose exception class matches, checked top to bottom.
  • The code demo above opens sample1.txt for reading; that file does not exist, open() raises FileNotFoundError, the friendly message prints, and the notebook keeps running — no crash, no red traceback.

The same pattern is used everywhere real programs live: opening files, validating input, calling APIs, parsing data. Wrap risk, react gracefully, and let the rest of the program continue.

3.6 try / except / else / finally — The Complete Flow

The full pattern is try → except → else → finally:

  • try — the risky code.
  • except — runs when an exception occurred (one or many, in specificity order).
  • else — runs only when try finished with no exception.
  • finally — always runs, whether an exception happened or not, even if try or except used return or raise.

finally is the natural home for cleanup: close a file, release a lock, commit or roll back a database connection. Because the language guarantees it runs on every exit path, resources never leak even when the flow is wild.

  1. Namespaces and the LEGB Rule

1.1 A namespace is a dictionary of names

A namespace is exactly what it sounds like: a space that holds names. Programmatically, it is a dictionary whose keys are identifiers (like a, temp, print) and whose values are the objects they refer to. Python maintains four of them around every piece of code:

Namespace What it holds
Built-in print, len, dict, max …
Global everything defined at the top of a module
Enclosing variables of outer functions around a nested function
Local names created inside the currently executing function

A scope is the textual region of the program where a given namespace is directly accessible — where a name can be used without a qualifier. The two concepts go together: the namespace is the dictionary, the scope is the territory.

When Python meets a name in your code, it does not guess — it searches from the inside out, strictly in this order: Local, Enclosing, Global, Built-in. The first hit wins. If no scope in the chain contains the name, Python raises NameError. Memorise the acronym LEGB; it is tested in interviews and it silently explains most of the surprising behaviour you will see in the code cells that follow — for instance, why a variable named a inside a function and a variable named a at the top level are two completely different objects living in different namespaces.

5.1 The metadata problem and functools.wraps

There is a subtle bug hiding inside every plain decorator. When @my_decorator reassigns hello = my_decorator(hello), the object now bound to hello is the wrapper function — and the wrapper carries its own metadata, not the original's:

The name, docstring, and even the signature that debugging tools, help(), and documentation generators rely on have been replaced by the wrapper's. The function behaves correctly but identifies incorrectly.

The fix lives in the standard library:

@wraps(func) copies __name__, __doc__, __module__, and the stored signature from the original function onto the wrapper, so an outer decorator no longer masquerades as a stranger. This is the universal professional convention — a decorator without @wraps breaks introspection, which is worse than it sounds: tracebacks, help(), and IDE tooltips all report the wrapper instead of the wrapped function.

Edge Cases and Boundaries

6.2 Deep dive — mutation across the call boundary

  • Objects are passed by reference into functions.
  • Mutation inside → the caller's object is affected: same object, shared memory.
  • Immutables (int/str): rebinding inside the function is invisible outside.
  • Mutables (list/dict/object): in-place changes are visible outside.
  • This causes classic bugs where a function silently rewrites caller data.
  • Defensive approach: copy the object inside the function first.
  • Mental model: variables are arrows, objects are boxes; function parameters copy the arrow, not the box.
