Real-World Hook: Hostel Mess Lunch 🏫

  1. The Four Import Styles

1.1 Style 1 — import module: The Whole Counter, Prefix Calls

The first and safest style is the plain import module. Think of it as lifting the entire counter over to your seat: every tool that counter offers is now available, but every tool is labelled with its counter name. You call math.sqrt(625) rather than a bare sqrt(625).

Why does this matter? Because labels prevent collisions. Python files reuse names freely — you might have a variable called sum or a function called random, anything. If every imported function came without a label, your variables and the library's names would fight for the same name, and whichever was defined later would silently win.

The code below imports math and immediately puts it to work:

  • math.sqrt(625) — the square root; 625 is a perfect square, so 25.0.
  • math.factorial(6) — 6! = 6 * 5 * 4 * 3 * 2 * 1 = 720.
  • round(math.pi, 4) — pi shortened to four decimals: 3.1416.
  • math.hypot(3, 4) — the hypotenuse of a right triangle with legs 3 and 4; Pythagoras gives 5.0.
  • math.gcd(48, 180) — the greatest common divisor, 12.
  • math.ceil(9.2) and math.floor(9.2) — rounding up to 10 and down to 9; they always move to the nearest whole numbers above and below.

Notice the pattern: import math creates a namespace, and you reach inside it with the dot operator. Later on, this habit — always going through a label — is the single best defensive habit in Python.

python
# 📦 STYLE-1: `import module` — pura-counter lift, naam-se-call!
import math

print("sqrt(625)  :", math.sqrt(625))
print("factorial 6:", math.factorial(6))
print("pi round-4 :", round(math.pi, 4))
print("hypot(3,4) :", math.hypot(3, 4))
print("gcd(48,180):", math.gcd(48, 180))
print("ceil 9.2   :", math.ceil(9.2), "| floor 9.2:", math.floor(9.2))
# Expected OUTPUT:
# sqrt(625)  : 25.0
# factorial 6: 720
# pi round-4 : 3.1416
# hypot(3,4) : 5.0
# gcd(48,180): 12
# ceil 9.2   : 10 | floor 9.2: 9

1.2 Style 2 — import module as alias: Give It a Short Stamp

Typing math.sqrt all day is fine, but some module names are long. Python lets you attach a short nickname with import module as alias. After import math as m, the name m refers to the exact same module object — there is only ever one math loaded — and you call m.hypot(5, 12) exactly as you would call math.hypot(5, 12).

The alias is your personal abbreviation, chosen by you, for you. It changes nothing about how Python resolves the import; it only changes the handle you use from that point on. Different files can even give the same module different aliases without conflict.

The same cell shows why datetime is a wonderful everyday module. Dates are objects, and objects know how to behave:

  • dt.date(2026, 9, 17) builds a fixed date — no time, no timezone, just the calendar day.
  • .strftime("%A") formats that date as the full weekday name, here "Thursday".
  • Subtracting two dates gives a timedelta, and reading .days tells you how many calendar days lie between them — here 106 days from 17 September 2026 to 1 January 2027.
  • Adding dt.timedelta(weeks=2) moves the date forward by fourteen days, landing on 1 October 2026.

This is the heart of library reuse: someone built the hard, fiddly calendar logic, and you get to say "add two weeks" in one readable line.

python
# 🏷️ STYLE-2: `import module as alias` — short-stamp nickname!
import math as m
import datetime as dt

print("m.hypot    :", m.hypot(5, 12))
today = dt.date(2026, 9, 17)                       # fixed-date (deterministic!) 📅
print("today      :", today, "| weekday:", today.strftime("%A"))
newyear = dt.date(2027, 1, 1)
print("days-left  :", (newyear - today).days, "(NY-2027 tak!)")
print("+2 weeks   :", today + dt.timedelta(weeks=2))
# Expected OUTPUT:
# m.hypot    : 13.0
# today      : 2026-09-17 | weekday: Thursday
# days-left  : 106 (NY-2027 tak!)
# +2 weeks   : 2026-10-01

1.3 Style 3 — from module import name: Grab Only the Dish You Need

Sometimes you want just one or two tools, not a whole counter. from math import hypot, factorial, comb pulls only those three names into your file, and after that line they can be called directly — comb(10, 5) — with no prefix at all.

This is the most convenient style when used sparingly, which is exactly why the pairing below is so instructive. The cell imports seed, randint, choice, and sample from random, then demonstrates the single most important idea in random programming: seeding.

Computers cannot produce true randomness by themselves — they compute, and computing is deterministic. random.randint(1, 6) doesn't roll a physical die; it reads the next value from a long mathematical sequence that looks random. That sequence is controlled by a seed: a starting number.

  • Set seed(42) and the sequence begins at a specific point.
  • Ask for three dice rolls and you get [6, 1, 1].
  • Call seed(42) again, and the sequence restarts at exactly the same point.
  • Ask for three dice rolls again and you get the same [6, 1, 1].

This is the superpower hiding inside "randomness": with a fixed seed, an experiment becomes reproducible. A failing test — or a paper you want to defend — can be re-run with identical results. seed() plus the random family turns lucky guessing into controlled science.

Also note comb(10, 5) = 252: the number of ways to choose 5 items out of 10, a preview of the "how many possible papers?" idea in the task notebook.

python
# 🥡 STYLE-3: `from module import name` — target-dish direct!
from math import hypot, factorial, comb
from random import seed, randint, choice, sample

print("booth-combo:", comb(10, 5), "ways")
seed(42)                                           # 🎲 same-seed = same-dice!
print("dice x3    :", [randint(1, 6) for _ in range(3)])
seed(42)                                           # re-seed: same-trick repeat!
print("redice x3  :", [randint(1, 6) for _ in range(3)], "← REPEAT ka proof!")
# Expected OUTPUT:
# booth-combo: 252 ways
# dice x3    : [6, 1, 1]
# redice x3  : [6, 1, 1] ← REPEAT ka proof!

1.4 Style 4 — from module import *: The Wildcard Trap

from math import * sounds incredibly convenient: "give me everything, no prefix, no fuss." It is — until it isn't. The star import takes every public name in the module and dumps it directly into your namespace. You don't get to choose; you get the whole counter thrown onto your plate.

The demonstration in this cell exposes the exact failure mode. Start with a plain user variable:

ceil = 99 — your own, perfectly reasonable integer.

If, at that point, you had executed from math import *, Python's math.ceil function would have stomped over your variable. Conversely, if you already have your own sum, min, or range, they would stomp over the library's. Whichever assignment happens last wins, and nobody gets a warning. That silent, order-dependent overwriting is called namespace pollution.

The prefix style math.ceil(9.2) is immune: your ceil and math's ceil live in different namespaces, so both can exist peacefully. The quote in this cell sums it up: prefix = the trustworthy road.

The markdown cell right after this demo lists the three concrete harms — pollution, origin confusion, and linter blindness. When you import 200+ names you can no longer tell where any of them came from, and tools that catch typos and shadowing go quiet. The professional rule of thumb: prefer import math or an explicit from math import ceil; reserve the star for quick interactive experiments at your own risk.

python
# ⚠️ STYLE-4: `from module import *` — sab-kuch NAKED-import ka big-bill!
# (demo WITHOUT-star: cool-concept explain; star-import pollution!)
print("ceil ke do-chehre — same-naam ke saamne:")
# Scenario: star-import ne `ceil` ko math.ceil se OVERWRITE!
import math
ceil = 99                                          # user-variable
print("user-ceil  :", ceil)
# agar `from math import *` kar diya hota:
# → math.ceil ne 'ceil' ko crush ho-jaata boom! (bhaari bill!)
print("math.ceil  :", math.ceil(9.2), "(prefix = bharosa raasta!)")
# Expected OUTPUT:
# ceil ke do-chehre — manas ke saamne:
# user-ceil  : 99
# math.ceil  : 10 (prefix = bharosa raasta!)

The Harm of import * (3-part warning!)

  1. Namespace pollution: 200+ names mix into your pocket — risk of your variables being hijacked (sum/min get taken over!)
  2. Origin confusion: where did this function come from? (maintenance nightmare 😵)
  3. Lint pain: IDEs/linters cannot track silent imports! > 🎯 Rule-card: for script clarity use import X or `from X import …

  1. Inspecting Modules

2.1 Peeking Inside with dir() and the Dunders

Modules can feel like black boxes until you learn to open them. Python gives you three instant inspection tools, all used in this cell:

  • type(math).__name__ — the class of the object, which prints "module". This confirms that a module is just another kind of Python object.
  • math.__name__ — the module's own name, "math". Every module knows who it is.
  • dir(math) — the complete inventory of names inside the module. Filtering out names starting with an underscore (_) removes the private machinery and leaves the public API: the functions the library authors intend you to call.

On this machine, dir(math) reveals more than sixty public tools. The letters acos, cbrt, comb, log, sin, and tan are all there — the entire counter, listed for free. In an interactive console, running dir(math) yourself is often faster than searching the documentation, because the answer is right there in the interpreter.

The double-underscore names you see when you don't filter are called dunders (double underscores). Attributes like __doc__, __file__, and __name__ are Python's metadata layer: they describe the module itself. Good libraries also give every function a __doc__ string, which lets you request help(math.sqrt) and read a plain-English description. If you write your own modules with docstrings (the next lesson), you are giving your teammates exactly the same luxury — a library that documents itself.

python
# 👀 Module peeping: `dir()` + module-name/type!
import math, random, datetime
print("math-module type:", type(math).__name__)
print("math.__name__   :", math.__name__)

peek = [n for n in dir(math) if not n.startswith("_")]
print("math's public-tools (first-10):", peek[:10])
print("total public  :", len(peek))
# Expected OUTPUT:
# math-module type: module
# math.__name__   : math
# math's public-tools (first-10): ['acos', 'acosh', 'asin', 'asinh', 'atan', 'atan2', 'atanh', 'cbrt', 'ceil', 'comb']
# total public  : (varies ~50+, signature version-stable head!)

  1. The Shadow Trap — Never Name a File Like the Standard Library

3.1 When Your Own math.py Silently Replaces the Real One

Here is an interview classic that has burned thousands of beginners — and a few professionals. Imagine you create a small helper file and, in a hurry, name it math.py. Somewhere else in the same project you write import math, expecting the square-root machine you have used all along.

Python looks for math by scanning its import paths. The directory containing your file is almost always on that search path — frequently before the standard library. So import math binds to your math.py, not the real one. The standard library is effectively hidden behind your file.

This is the shadow trap: a local module that shadows (overwrites) a standard-library name. Now every call to math.sqrt, every alias, and every learning snippet that depends on the real math silently breaks — or worse, from math import sqrt imports your file's sqrt, which may not exist at all.

The fix is absurdly simple: choose a different filename. The hall of shame names the usual suspects — math.py, random.py, datetime.py, json.py, os.py, types.py, email.py, test.py. If your file is on that list (or could be mistaken for any stdlib module), rename it before you import anything.

The complete live proof appears in the task notebook: a temporary fake math.py is created, sys.path is pointed at it first, and import math really does pick up the fake. After cleanup, the genuine standard-library math comes back. Seeing it happen once is worth a thousand warnings.

Summary

We used math for number drills, random with a fixed seed(42) to prove deterministic replay, and datetime to subtract dates and add timedeltas. Inspecting a module with dir() and reading its dunders such as __name__ and __doc__ gives you a free tour of its public API. Finally, the shadow trap warns us never to name our own file math.py (or any stdlib name) — a mistake that silently hides the real library and breaks every dependent import.

You are no longer only a user of modules — you are their author. A package is a folder of related modules marked by an __init__.py — the index-card that executes on first import, prints a banner, and re-exports shortcuts such as from .billing import total_bill. Virtual environments isolate every project's dependencies so conflicting library versions never fight. Making Your Own Module — The First Box of Your Own Library

Real-World Hook: One Recipe Book for Every Kitchen

After two launched projects, you notice a pattern: you are writing the same helper functions again and again — averaging marks, mapping scores to grades, picking the topper. Photocopying those helpers into every new notebook works for a while, but every bugfix now has to be repeated in every copy.

The smart idea: one recipe book — a single grade_utils.py that every counter imports. Fix the recipe once; every kitchen benefits. That is the entire philosophy of modules: write code once, reuse it with an import, treat your own file with the same respect you give the standard library.

📖 Definitions (interview-grade)

module — any .py file that can be imported. import cycle — 1) look in the sys.modules cache; 2) scan the folders in sys.path; 3) found → execute the file → bind the namespace.

The first cell below walks you through this exact cycle in a few lines of code.

  1. Your First Module — Write, Point, Import

1.1 A module is just a .py file

There is nothing magical about a module. It is a plain Python file that defines functions, classes, and variables at the top level. When you run import grade_utils, the interpreter looks for a file called grade_utils.py in the folders listed in sys.path. If it is found, Python executes the file once, collects every top-level name into a module object, and binds that object to the name grade_utils. If the file is not found, you get ModuleNotFoundError.

The demo writes a real module with open(). It contains three functions: average(marks_list) computes round(sum / len, 1), grade_letter(score) maps numbers to A/B/C/D/F through if thresholds, and topper(students) returns the name with the highest score using max(students, key=students.get). That key= trick is worth remembering: max compares dictionary values when you give it the get method as the key function.

Then comes the punctuation mark: sys.path.insert(0, tmp). The temp folder now leads Python's search list, so the freshly written file becomes importable. The alias import grade_utils as gu shortens the namespace, and now every function is one dot away: gu.average(...), gu.grade_letter(...), gu.topper(...).

sql
# 🐣 STEP-1: Apna grade_utils.py likho + import karo! (tempdir-magic-live ✨)
import sys, os, tempfile

MODULE_CODE = '''"""grade_utils — Student-marks ke helper-functions ki library! 📚"""

def average(marks_list):
    """Marks-list ka average nikaalo (round-1!)."""
    return round(sum(marks_list) / len(marks_list), 1)

def grade_letter(score):
    """90:A, 75:B, 60:C, 40:D, <40:F — exam-card style!"""
    if score >= 90: return "A"
    if score >= 75: return "B"
    if score >= 60: return "C"
    if score >= 40: return "D"
    return "F"

def topper(students):
    """{'name': marks} dict me se sabse-badiya-student name!"""
    return max(students, key=students.get)
'''

tmp = tempfile.mkdtemp()
with open(os.path.join(tmp, "grade_utils.py"), "w") as f:
    f.write(MODULE_CODE)

sys.path.insert(0, tmp)              # python ko BATO: "yahan bhi dhekh!" 🗺️
import grade_utils as gu             # 🎉 private-library live!
    # ...
# Expected OUTPUT:
# average: 80.0
# grade 88: B
# topper  : Priya

1.2 Module peeping — dir() and docstrings

A module should be able to explain itself. The built-in dir(module) lists every name the module exposes — functions, variables, and also dunder machinery like __name__ and __doc__. The demo filters those out with [n for n in dir(gu) if not n.startswith("_")], leaving exactly the public surface: ['average', 'grade_letter', 'topper']. That is a perfect sanity check: the module shows only what we designed it to show.

The second self-explanatory tool is the docstring. The triple-quoted comment at the top of the file becomes gu.__doc__ — the module's own one-line biography. Each function's docstring is equally queryable: gu.average.__doc__ prints what average promises to do. In an interactive console, help(gu.average) renders the signature and docstring into a tidy card.

Why does this matter at scale? Because documentation that lives next to the code cannot rot: it is regenerated from the file itself. When you revisit a module months later, __doc__ and dir() give you an instant, accurate map.

python

1.3 The import cache — sys.modules

Run the same import twice and you might expect the file to execute twice. It does not. Python keeps every loaded module in a dictionary called sys.modules, keyed by the module's name. The first import grade_utils executes the file and stores the result. A second import grade_utils as gu_2 finds the name already cached and returns the same object without re-reading the file — hence gu is gu_2 prints True.

This cache is a performance feature: importing a heavy module (imagine hundreds of functions) would otherwise be catastrophically slow. But it is also the classic footgun in notebooks: after you edit your .py file on disk, re-importing still gives you the stale cached version. The official cure is importlib.reload(module), or simply restarting the kernel. The rule to internalise: a module executes exactly once per process — the cache is your friend until you are actively editing, and then it feels like an enemy.

python
# 🗄️ STEP-3: sys.modules cache — "already-load hai ji!" proof!
print("in-cache?   :", "grade_utils" in sys.modules)

# dobara-import: NAYA-execute NAHI — cache-se le-te! (speed-priya!)
import grade_utils as gu_2
print("same-object?  :", gu is gu_2)
print("(cache-rule → import 2nd-time CHEAP; test-fixes require reload!)")
# Expected OUTPUT:
# in-cache?   : True
# same-object?  : True
# (cache-rule → import 2nd-time CHEAP; test-fixes require reload!)

  1. The Two Lives of a File

2.1 Import-silent vs script-loud

Every Python file has two possible lives. If you run python myfile.py in a terminal, the file is a script: its top-to-bottom code executes, prints fire, and it behaves like a program. If you import myfile from elsewhere, the file is a module: functions and classes load, but you usually do not want its demo prints and test blocks cluttering your session.

How does Python know which life a file is living? It sets a magic variable, __name__:

  • when the file is executed directly → __name__ == "__main__" 🎬
  • when the file is imported → __name__ == "file's own name" (e.g. "loud_fetcher")

The idiom if __name__ == "__main__": therefore arms a block that fires only in script mode. The next cell builds a module with an unguarded loud print (“loud-banner-at-import”) and a guarded print (“script-mode special-lines”). On import, only the banner fires; the guarded line stays silent — exactly the professional behaviour you want from a library.

2.2 Running the same file as a script — subprocess

The previous cell proved what import-time silence looks like. This cell proves the sunny side: the same file, launched directly, becomes chatty. To launch it, we need a brand-new Python process — not the notebook's kernel — so the demo uses subprocess.run([sys.executable, script_path], capture_output=True, text=True).

sys.executable is the full path of the Python interpreter currently running the notebook — passing it guarantees we use the very same Python. capture_output=True captures the child's stdout into result.stdout, and text=True decodes it as text (instead of bytes). result.stdout.strip() then gives us exactly what a terminal user would have seen: both the banner AND “script-mode special-lines!”, because in script mode __name__ is "__main__".

The contrast between the two cells is the whole lesson: the guard makes one file behave as a quiet library when imported and as a loud program when executed. Finally, the cleanup (sys.path.pop(0) twice, plus evicting both modules from sys.modules) restores the environment so later cells start fresh.

Rule to write down: put demo code, self-tests, and “run-me” examples inside the guard block. That way your module stays quiet and polite when somebody imports it, yet fully alive when launched directly. Every serious Python file you will read in the wild obeys this rule.

1.3 Three import styles for packages

Packages multiply the import options you already know:

Style A — package-level re-export. Because __init__.py did from .billing import total_bill, the name total_bill became part of the package's top level. dukan.total_bill(1000) → 1050.0 (1000 + 5% tax) works with no submodule import at all. This is why __init__.py is called the shortcut-maker.

Style B — dotted submodule import. from dukan.billing import tax descends folder → file → name, then you call bare tax(2000) → 100.0. The dotted path is explicit about where the function lives — great for readability and for linters to trace.

  1. Relative Imports — Wiring Inside the Package

2.1 Dots mean “inside this package”

Submodules often need each other. How does billing.py reach the price board in catalog.py? Through a relative import: from .catalog import ITEMS. The single leading dot means “the package I live in”, so the path is resolved relative to the current module's package, not the project root.

That is what __init__.py did with from .billing import ... — the dot says “billing, my sibling, in my package dukan.” Relative imports keep package wiring portable: you can rename the outer project folder or move the whole package, and the internal connectors still work, because they are relative to the package, not absolute.

2.2 The one sharp rule: never run a submodule directly

Relative imports work only when the file is loaded as part of its package — i.e. reached through an import like import dukan or from dukan import billing. If you try python dukan/billing.py, Python treats billing.py as a standalone script with no enclosing package, the leading dot has nothing to resolve, and you get ImportError: attempted relative import with no known parent package.

The practical consequence is the golden layout: entry files (the ones you run) sit in the root folder; submodules are only imported, never executed directly. The cell below states this as a set of rules to carry into your own projects.

Virtual Environments — Your Own Kitchen for Every Project

Real-World Hook: The Kitchen-War of 2 Projects

Project-A (a pizza app 🍕) needs cheese_lib v1; Project-B (a salad dash 🥗) needs cheese_lib v2 with the same name. In ONE global microwave (global pip!) only one can be installed — a nasty tug-of-war: whoever installs last is the winner, and the other project breaks.

The root solution: a separate kitchen for every project. Separate counters, separate lib-versions, separate pip-life — no war. A virtual environment is exactly that kitchen: an isolated folder holding its own python, its own pip, and its own libraries, completely locked away from the base system.

📖 Definition (interview-grade)

Virtual Environment = an isolated folder that owns its own python, its own pip, and its own installed libraries, fully separated from the system-level installation. activate = the entry pass 🎫 that makes your shell use that folder's tools; deactivate = leaving the kitchen.

The live demo next will build one of these kitchens and inspect its rooms.

  1. Creating a Kitchen — venv Anatomy

The venv concept is simple; the folder it creates is a small, organised world. The next cell runs python -m venv <folder> and then inspects what was built.

1.1 What python -m venv creates

python -m venv myenv builds a new self-contained Python world inside the folder myenv. Inside it you will typically find:

Entry Purpose
bin/ (Linux/macOS) or Scripts/ (Windows) launcher scripts: your own python, pip, plus the activation scripts (activate, Activate.ps1, activate.csh)
lib/ (or Lib/) the private site-packages where your env's libraries get installed — isolated from the global site-packages
include/ C-extension headers used when building packages with native code
pyvenv.cfg the config card pointing back to the base (system) Python that spawned this env
.gitignore a polite helper so you do not accidentally commit the heavy env folder (newer versions add it automatically)

The demos use a temp directory for the environment, but in a real project you would create myenv right inside the project folder. 1.2 Proof of isolation — sys.prefix vs sys.base_prefix

How do we prove an environment is actually isolated rather than just a folder with a nice name? We ask the environment's own Python two questions and compare the answers.

  • sys.base_prefix — the location of the base (system) Python that created the environment.
  • sys.prefix — the location of the Python that is currently running.

Inside a virtual environment these two differ: sys.prefix points into your env folder while sys.base_prefix still points at the system Python. The check sys.prefix != sys.base_prefix therefore prints True — the mechanical proof that demov/bin/python is running inside its own isolated world. Outside an environment, in the base interpreter, both values are equal and the check prints False.

The cell also runs pip list from the env's own pip: a fresh environment contains almost nothing (just pip and setuptools on classic builds) — the clean slate that guarantees no global packages leak into your kitchen. Two numbers (prefix mismatch) and a short package list tell you everything: interpreters differ, libraries are empty — you are truly isolated.

The anatomy note after the demo reminds you how Windows mirrors everything under Scripts/\activate instead of bin/activate, and why keeping envs out of git is the industry rule.

Common Mistakes and Pitfalls

5 Common Mistakes

# ❌ Mistake ✅ Correct
1 from math import * again and again prefix-style import math for safety
2 your filename = stdlib (math.py) shadow-trap give your files a different name! 🪤
3 from random import * + your own sample() clash use only from-name-import (explicit!)
4 mixing string-dates in datetime.date() parse the text → datetime.strptime
5 thinking seed = "always lucky" seed is only a deterministic repeat (testing tool!) 🎲

🎯 Toolbox-card: math=numbers-pump ⛽ · random=seeded-luck 🎲 · datetime=calendar-train 🚂 — install-free, docs-rich, import just this!

# Mistake Correct habit
1 unguarded loud prints in a module file protect with if __name__ == "__main__": 🔑
2 leaving temp folders crammed into sys.path after the demo pop them out + evict from sys.modules 🧹
3 "I edited my file but the old result keeps coming back!" the import cache! use importlib.reload(module) 🔄
4 scattering imports deep inside functions keep imports at the top of the file (PEP 8) — unless genuinely needed at runtime
5 filenames with spaces, dashes, or capitals lowercase snake_case is the Python way 📁

Cache principle: importing the same module a second time is nearly free (the cache serves it); the first import executes the whole file. The guard is what keeps that one-time execution from being noisy.

# Mistake Correct habit
1 forgetting __init__.py (a plain folder, not a package!) add __init__.py — even a docstring-only one is enough 📁
2 heavy compute inside __init__.py (slow import!) keep init light: shortcuts and banners, not business logic 🐌
3 running a submodule directly: python dukan/billing.py keep entry files at the root; let the package be imported from above 🧭
4 from dukan import * — pollution travels to packages too use explicit names or dotted imports
5 package names in CAPITALS or with dashes lowercase snake_case is the ecosystem standard 📁

🎯 Import-resolution map: cache → path-scan → folder-peep → __init__-execute → dotted-binds. Understanding each step makes any package mystery solvable in minutes.

# ❌ Mistake ✅ Correct
1 installing EVERYTHING global-pip on one machine venv-per-project (war-avoid!) ✌️
2 randomly mixing conda+pip in the same-env first conda-big, then pip-rest — COLD-ORDER!
3 tearing up requirements.txt without a freeze on every change pip freeze > ... sync! 📋
4 expecting uv everywhere (WSL/termux issues sometimes!) pip+venv as the reliable-fallback 🌱
5 tool-hoarding (setting everything up at once!) need-driven pick (matrix-rule!) 🗺️
